# integration-qa

백엔드(Spring Boot)와 프론트엔드(React+TS) 사이의 경계면을 검증하는 절차다. 대상은
`_workspace/contract/`에 고정된 계약이 실제 구현 두 쪽 모두에서 지켜지고 있는지다.

## 핵심 철학: "존재 확인"이 아니라 "경계면 교차 비교"

파일이 있는지, 함수가 정의되어 있는지 확인하는 것은 QA가 아니다. integration-qa의 본질은
**같은 값이 오가는 두 지점을 동시에 열어 나란히 대조하는 것**이다 — 백엔드 Controller/DTO가
실제로 내려보내는 필드명·타입·구조와, 프론트 API 클라이언트/TS 타입이 그것을 어떻게 기대하고
있는지를 한 화면에 놓고 글자 단위로 맞춰본다. Why: 두 구현이 각자 컴파일에는 성공하고 각자
단위 테스트도 통과할 수 있다 — 문제는 항상 "둘 사이"에서 발생하고, 그 둘 사이를 보는 것은
이 스킬만 한다. 한쪽만 보고 "괜찮아 보인다"고 판단하지 마라.

## 대조 체크리스트

각 엔드포인트마다 아래 항목을 백엔드 코드와 프론트 코드에서 각각 확인하고 나란히 비교하라.

| 항목 | 백엔드에서 확인할 곳 | 프론트에서 확인할 곳 |
|------|----------------------|----------------------|
| 엔드포인트 경로 | `@RequestMapping`/`@GetMapping` 등 경로 | `src/api/*.ts`의 요청 URL 문자열 |
| HTTP 메서드 | 컨트롤러 애노테이션 | axios 호출 메서드(`get/post/patch/delete`) |
| 요청 바디 필드명/타입 | 요청 DTO 클래스 필드 | 요청 시 보내는 객체/타입 정의 |
| 응답 필드명/타입/중첩구조 | 응답 DTO 클래스 필드 및 중첩 DTO | `src/types/contract.ts`의 대응 인터페이스 |
| 상태코드 | 성공/예외 시 실제 반환 상태 | 에러 처리 분기(401/403/404/409 등) |
| 인증 헤더 | `SecurityConfig` 인증 필요 경로 | 인터셉터가 헤더를 붙이는 조건 |
| CORS 허용 오리진 | `SecurityConfig`/`CorsConfigurationSource` | 프론트 `baseURL`/개발 서버 포트 |
| 날짜/숫자 직렬화 | Jackson 기본 직렬화 결과(ISO 8601 여부) | 프론트에서 파싱/포맷하는 방식 |

각 셀은 "본다"가 아니라 "일치 여부를 판정한다"까지 마쳐야 완료로 친다. 하나라도 불일치하면
즉시 기록하고 다음 항목으로 넘어간다 — 하나를 고칠 때까지 멈추지 않는다. 나머지도 모두 훑어
전체 불일치 목록을 먼저 확보한 뒤 리포트로 넘긴다.

## 점진적(incremental) QA

전체 구현이 끝난 뒤 한 번에 몰아서 검증하지 않는다. 모듈이 완성되는 즉시 검증한다.

권장 순서(의존성 기준): **인증 → 상품 → 장바구니 → 주문/결제**

Why: 인증 모듈의 계약 어긋남(예: 로그인 응답의 토큰 필드명 불일치)을 초기에 잡지 못하면,
그 위에서 동작하는 장바구니·주문 모듈 전부가 "인증 안 됨"으로 오작동하면서 실제 원인이
아닌 곳에서 증상이 나타난다. 초기 계약 어긋남은 뒤 모듈로 전파되며 디버깅 비용을 눈덩이처럼
불린다. 각 모듈이 완료 신호를 보내는 즉시 그 모듈만 검증하고, 통과해야 다음 모듈 검증으로
넘어간다는 전제를 오케스트레이터와 공유하라.

## 실제 실행 검증

문서·코드 대조만으로 끝내지 않는다. 아래를 실제로 실행해 컴파일/빌드 통과를 확인한다.

1. **백엔드**: `./gradlew build` 또는 `mvn test`를 실행한다. 실패하면 실패 로그의 핵심 원인을
   그대로 리포트에 인용한다.
2. **프론트 타입체크**: `tsc --noEmit`을 실행해 타입 오류가 없는지 확인한다.
3. **프론트 빌드**: `vite build`(또는 `npm run build`)를 실행해 빌드 오류가 없는지 확인한다.
4. **가능하면 실제 호출 검증**: 백엔드 서버를 기동할 수 있으면 대표 엔드포인트를 `curl`로
   직접 호출해 실제 응답 JSON의 필드명/구조가 계약·프론트 타입과 일치하는지 확인한다.
   예: `curl -s http://localhost:8080/api/products | jq .`
   서버 기동이 불가능한 환경이면 이 단계는 생략하되 리포트에 "서버 미기동으로 실행 검증 생략"을
   명시한다.

빌드 실패는 절대 "완료"로 간주하지 않는다. 코드 대조가 전부 일치해 보여도 컴파일이 깨지면
그 모듈은 미완료다.

## 자주 나오는 경계면 버그 패턴

아래는 반복적으로 나타나는 불일치 유형이다. 대조 시 특히 이 패턴들을 의심하라.

- **필드명 표기 불일치**: 백엔드가 `product_id`(snake_case)로 직렬화하는데 프론트는
  `productId`(camelCase)를 기대. Jackson 설정(`@JsonNaming` 등)이 계약과 다르게 걸려 있을 때 발생.
- **중첩 객체 vs 평탄화**: 계약은 `{ product: { id, name } }`처럼 중첩을 기대하는데 백엔드가
  `{ productId, productName }`으로 평탄화해 응답하거나 그 반대.
- **nullable 처리 불일치**: 백엔드가 특정 필드를 옵셔널로 두고 null을 내려보내는데 프론트
  타입은 필수(non-optional)로 선언되어 있어 런타임에만 드러나는 경우.
- **페이지네이션 래핑 유무**: 계약상 `{ items, totalCount }`로 감싸기로 했는데 실제로는
  배열을 그대로 반환(또는 그 반대)하여 프론트가 `.items`를 읽다가 `undefined` 발생.
- **인증 헤더 누락**: 프론트가 특정 API 호출에서 인터셉터를 우회하거나(직접 axios 호출),
  백엔드가 실제로는 인증이 필요한데 계약에 "불필요"로 잘못 기재되어 있는 경우.
- **에러 포맷 이탈**: 특정 예외 경로만 표준 에러 포맷을 따르지 않고 스프링 기본 에러 페이지나
  다른 shape을 반환하는 경우(주로 GlobalExceptionHandler가 잡지 못하는 예외 타입).

## 리포트 규칙

불일치를 발견하면 `_workspace/qa-report.md`에 아래 형식으로 기록한다. 코드 위치는 파일 경로와
줄 번호를 명시해 담당 엔지니어가 바로 찾아갈 수 있게 한다.

```markdown
## [모듈명] 불일치 #N

- **항목**: 응답 필드명
- **백엔드**: `backend/.../ProductResponse.java:18` — `product_id`
- **프론트**: `frontend/src/types/contract.ts:9` — `productId`
- **기대(계약)**: `_workspace/contract/api-spec.md` 기준 camelCase `productId`
- **영향**: 상품 상세 페이지에서 `undefined` 참조 발생
- **담당**: backend-engineer (계약과 다르게 직렬화된 쪽 수정)
- **상태**: 미해결
```

- 모듈별로 섹션을 나누고, 검증 통과 항목도 "통과" 목록으로 짧게 남겨 어디까지 검증했는지
  추적 가능하게 한다.
- 불일치를 발견하면 즉시 담당 엔지니어에게 SendMessage로 전달하고, 재검증 후 해당 항목의
  "상태"를 "해결"로 갱신한다. 리포트 파일이 항상 최신 상태를 반영하게 한다.
- 같은 유형의 불일치가 반복(2회 이상)되면 개별 수정으로 끝내지 말고, 계약 자체가 모호했던
  것은 아닌지 api-architect에게 피드백하여 근본 원인을 계약 단계에서 명확히 하도록 요청한다.

## 완료 판정 기준

해당 모듈의 미해결 불일치가 0건이고, 백엔드 빌드/테스트와 프론트 타입체크/빌드가 모두
통과했을 때만 그 모듈을 완료로 처리한다. 하나라도 미해결이면 완료로 보고하지 않는다.
